议会玩法重构执行计划

这份计划把脑暴方案转成当前 Godot 原型的落地路径。目标是在保留现有美术、角色、场景和大部分界面资产的前提下，把核心循环从“法器统治/情报解谜”替换为“议会罪行投票/阵营博弈”。

状态：待讨论 不立即开工 目标引擎：Godot 4.6.2 日期：2026-05-11

一、方案判断

应该保留

  • 现有角色立绘、NPC 选择卡、对话场景和背景资产。
  • 现有对话 UI、历史记录、状态页、设置页、结算页的视觉框架。
  • LLM 调用层：llm_client.gd 和 prompt 构建的基本结构。
  • 章节 JSON 加载模式和测试脚本组织方式。

应该替换

  • 法器、背包、商店、升级、统治需求作为核心玩法。
  • 世界情报卡作为主要胜负条件。
  • 暗杀、决斗、赠送法器、施法等旧行动按钮。
  • NPC 围绕法器需求和好感度推进的旧策略。

应该新增

  • 阵营、罪行、公开投票、投票倾向、政治交易、处决连锁。
  • 对等信息模型：所有角色只知道公开信息和自己的隐藏信息。
  • 前三章固定规模：4 人、9 人、12 人。
  • 可读的投票板、罪行板、公开信仰板和遗嘱投票日志。
最重要的设计转向：不要让玩家猜 LLM 心里有什么剧本，而是让玩家观察公开记录、推断谁害怕哪条罪、谁在保护哪个阵营。

二、目标体验

玩家看到的东西 玩家做的判断 系统提供的反馈
本章罪行库、全部议员、公开投票、公开倾向。 某个 NPC 是否害怕某条罪行，是否在保护同阵营者。 投票板立即更新，处决阈值清晰可见。
NPC 在对话里劝说、撤退、表态、要求交易。 这句话是软承诺、真威胁，还是诱导玩家先投票。 倾向可改，正式投票不可改，交易绑定不可撤销。
有人被处决，身份暂不公开，只留下遗嘱投票。 刚才杀掉的是盟友、敌人，还是关键摇摆票。 第二章起，遗嘱投票可能触发新处决，形成可复盘的连锁。

三、数据模型

建议新增一套议会玩法数据字段，先与旧字段并存，再逐步替换 UI 读取来源。

对象 新增字段 说明
GameState council_members、crime_pool、factions、vote_records、vote_tendencies、public_faction_support 替代旧的 artifacts、world_intel、shop 核心循环。
议员 id、public_name、portrait、scene、hidden_faction、hidden_crimes、alive、faction_revealed 玩家也是议员，和 NPC 使用同一种数据结构。
罪行 id、title、topics、source_note、chapter_tags 罪行标题用于 UI 和投票，source_note 只用于文档/调试，不一定进正式游戏文本。
投票 crime_id、member_id、vote、locked、source、round vote 为 guilty / innocent / abstain；正式投票 locked=true。
交易 offer_id、members、bound_votes、accepted 政治交易本质是一次批量锁定投票。

四、章节配置

章节 配置 验收目标
第一章 4 名角色，2 个阵营，5 条罪行，每人 5 选 3；2 票处决。处决发生后剩余 3 人强制公开阵营并结算。 10 分钟内完成一局，玩家能理解投票会直接杀人，并理解“少于等于 3 人强制公开”的终局规则。
第二章 9 名角色，3 个阵营，8 条罪行，每人抽 3 条。 玩家开始通过交易和投票行为推断阵营。
第三章 12 名角色，3 个阵营，10 条罪行，每人抽 3 条，强化遗嘱投票和连锁压力。 大局仍然可读，投票板不会淹没玩家。

计划新增 project/data/council_chapter_01.json、council_chapter_02.json、council_chapter_03.json。旧 chapter_01.json 保留，直到新模式稳定。

五、规则引擎

建议新增 CouncilRulesEngine，不要在旧 RulesEngine 上直接硬改。旧引擎可作为回滚路径。

核心 API

  • start_council_chapter(state, chapter_data)
  • record_tendency(member_id, crime_id, tendency)
  • cast_vote(member_id, crime_id, vote, source)
  • accept_trade(trade_offer)
  • check_executions()
  • apply_death_will(member_id)
  • check_faction_victory()

关键规则

  • 正式投票不可更改，倾向可更改但保留历史。
  • 处决阈值为总议员人数的一半向上取整；4 人局即 2 票处决。
  • 处决某罪行时，所有拥有该隐藏罪行的存活议员死亡。
  • 死亡议员留下全罪行遗嘱投票。第一章会记录但无实际影响，因为死亡后立即结算；第二章起正式参与连锁。
  • 存活者公开支持某阵营超过半数则该阵营胜利。
  • 任意结算检查时，若存活议员小于等于 3 人，强制公开阵营并结算。

六、LLM 改造

LLM 不再负责“自由地推进剧情”，而是负责在公开信息约束下选择清晰行动。

模块 改造内容 输出 JSON
PromptBuilder.npc_dialogue_* 注入 NPC 自己的隐藏阵营、隐藏罪行，以及所有公开投票/倾向。不注入任何其他人的隐藏信息。 speech、action、target_crime_id、vote、trade_offer
玩家角色 LLM 正式玩法只能通过行为文件驱动玩家角色。玩家本人不直接替角色投票或发言；玩家角色 LLM 同样只看公开信息和自身隐藏信息。 speech、action、target_member_id、target_crime_id、vote
动作约束 允许四类行动：撤退、直接投票、政治交易、倾向表达。旧 invite / duel / assassinate / gift / cast 暂停。 retreat、cast_vote、offer_trade、declare_tendency
LLM 输出必须被规则引擎校验。比如 NPC 不能投不存在的罪行，不能改已锁定投票，不能知道别人隐藏罪行，不能直接宣布胜负。

七、UI 改造

现有界面 新用途 优先级

九、执行阶段

阶段 0：模式开关与旧系统隔离

半天
  • 新增配置 game.mode = "council" 或启动常量，允许旧模式回滚。
  • 主流程根据模式加载旧 chapter_01.json 或新 council_chapter_01.json。
  • 隐藏新模式中无关的商店、背包、升级入口，但不删除系统和资源。

阶段 1：无 LLM 纸面模拟版

1-2 天
  • 实现议会数据模型和 CouncilRulesEngine。
  • 用测试脚本模拟玩家角色和 NPC 的投票、倾向、交易、处决；正式 UI 不提供玩家本人直接投票入口。
  • 完成第一章 4 人局，先不接入真实 LLM。
  • 新增规则测试：阈值、锁票、处决、第一章立即结算。

阶段 2：最小可玩 UI

2-3 天
  • 改造 NPC 选择页和对话页按钮。
  • 新增或改造状态页为投票板。
  • 议会状态页按“中间罪行、左侧有罪头像、右侧无罪头像、最右全员状态头像”实现；倾向用灰色头像，已投票用彩色头像。
  • 每回合对话结束后强制进入议会状态页，玩家点击“继续”后再回到对手选择页。
  • 完成第一章从开局到结算的完整手动流程。

阶段 3：LLM 决策接入

2-4 天
  • 重写 NPC prompt：自保优先、阵营胜利其次、只看公开信息。
  • LLM 输出四类行动 JSON，规则引擎做合法性校验。
  • 对非法输出做降级：只保留 speech，并记录“无有效行动”。
  • 完成第一章真实 LLM 可玩测试。

阶段 4：第二章和第三章内容扩展

2-3 天
  • 新增 9 人局和 12 人局章节 JSON。
  • 接入蓝领带党、红帽子党、绿果汁党三阵营随机分配。
  • 从 20 条罪行库中为章节选择 8 条和 10 条。
  • 第二章正式启用遗嘱投票；第三章进行连锁处决压力测试。

阶段 5：体验打磨与复盘

持续
  • 优化投票板可读性，减少大局信息噪音。
  • 结算页展示隐藏罪行、隐藏阵营、关键误杀和背叛链。
  • 调整罪行库标题，让每条罪行都像可以被议会审判。
  • 根据实测调整 LLM 行动概率，避免 NPC 过早锁死局面。

十一、风险与对策

信息过载

第二、三章投票记录可能太多。对策：默认只显示每条罪行的摘要，点击展开投票人和历史倾向。

LLM 乱编隐藏信息

对策：prompt 明确禁止，规则引擎只接受结构化行动，UI 只显示系统确认过的公开事实。

第一章太快结束

对策：这是教学目标，但可以要求至少经过 1 次会谈后才能正式投票。

NPC 过度自保

对策：策略权重里加入阵营胜利和交易收益，避免所有人永远只投无罪。

玩家缺少行动感

对策：把“直接投票”和“政治交易”做成强反馈按钮，投票后立刻刷新阈值和危险提示。

旧系统牵连太深

对策：以新模式并行实现，不在第一轮删除旧字段和旧 UI 资源。

十二、已确认决策

问题 决策 执行影响
第一章处决后如何结算 处决发生后只剩 3 人，因此强制公开阵营并结算。 第一章不需要额外“被处决者阵营失败”规则，统一走小于等于 3 人强制公开流程。
处决阈值 阈值为总人数一半向上取整；四人局 2 票处决。 规则引擎统一使用 ceil(total_members / 2)。
玩家控制方式 玩家只能通过行为文件驱动玩家角色。 正式 UI 不提供“真人直接投票/发言”的主流程按钮，会议行动由玩家角色 LLM 根据行为文件触发。
遗嘱投票 第一章会进行但没有实际作用；第二章正式启用。 第一章可记录遗嘱投票用于教学和复盘，但不再触发实际连锁。第二章起参与处决循环。
现实事件罪行 正式进入游戏文本。 罪行标题可以直接进入章节数据；原始事件备注可保留在内部文档或调试信息，不一定展示给玩家。
旧背包/法器/商店系统 暂时隐藏并保留系统。 实现时不要删除旧资源和逻辑，使用模式开关隔离。
对话页布局 主体保持现有大角色、大场景、对话框布局；底部仍是对话窗口；左侧为四类会议行动按钮，右侧为系统按钮。 后续 UI 实现只替换两侧按钮，不重排对话页主体，不把罪行快捷条放到底部。
回合结束流程 每回合对话结束时强制显示议会状态页；点击“继续”后回到对手选择页。 流程从“对话结束直接选人”改为“对话结束 → 状态复盘 → 继续 → 三选一”。

十三、建议的第一步

如果这份计划方向确认，第一步不要直接大改 UI，而是先做“阶段 1：无 LLM 纸面模拟版”。也就是新增议会状态和规则引擎，用测试脚本跑第一章 4 人局，确认投票、处决、结算真的成立。等规则跑顺，再接 UI 和 LLM。
